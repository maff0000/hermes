Cadence in source:

- Candle latest and history: written when the aggregator completes a bar (`main.py:L880-891`), so the key holds the **last completed** bar; its publish time is close to the bar close. The candle publish call runs only if the SQL save of that candle succeeded (`main.py:L884-891`), so a database write failure also suppresses the Redis candle (PARTIAL; live behaviour UNVERIFIED). The status `FORMING` exists in the contract but the aggregator path emits completed candles only (PARTIAL; live behaviour UNVERIFIED).
- Indicators, features, sessions, levels, control plane: a 60 second runner loop (`utils/hermes_publisher_runtime_v1.py:L26`). An indicator payload for a just-closed bar can therefore lag the candle by up to one loop interval plus compute time, and the two keys are not written atomically.
- Quote: 5 second loop. Tick: per stream tick.

Observed lag, validity window and cadence: `PENDING HELM PROTOCOL`.

## 5. Warm-up and historical depth (Scope 5)

Source facts:

- Indicators are computed from the closed-bar history sorted set, not from the latest key (`steps:L98-108`, L612-630). History depth gates every indicator.
- Read windows: 60 bars for the standard family, 210 bars for ema_200 (`steps:L48`, L63-64).
- Retention: M1 to H1 by a configured number of days with no default in code (`candle_history_v1.py:L42-61`); a comment records a DEV ruling of 14 days (L38). H4 keeps 250 bars by count (L76). D1 keeps 35 by count with a minimum of 26 for D1 indicators (`candle_d1_history_v1.py:L41-46`).
- Production Redis starts clean and is warmed from SQL plus live flow (`docs/architecture/environment-model.md:L87`); warm-start seeding code exists (`main.py:L1459-1471`, `utils/candle_h4_hydration_v1.py`, `utils/candle_d1_hydration_v1.py`).
- Source-level conclusion: ema_200 is reachable on M1, M5, M15, H1 and H4 given enough retained history, and structurally unreachable on D1; ema_50 is structurally unreachable on D1. Both are PROVEN from constants.

Observed index lengths, first/last bar open, gaps (H4 explicitly) and warm-up sufficiency per timeframe: `PENDING HELM PROTOCOL`. The protocol derives first and last bar open times from the history key names returned by the inventory scan (the epoch is part of the key name), which avoids any sorted-set range read above the approved cap.

## 8. Failure and staleness semantics (Scope 8)

From source: a candle's `status` is computed once at write time from its own age (`candle_contract_v1.py:L189-208`); nothing rewrites it later, so freshness must be judged from `valid_until_utc` and the observer's clock. The documented consumer rule agrees (`utils/hermes_control_plane_v1.py:L319`). A stale-but-present state exists for persistent keys. The step that builds the heartbeat does compare `valid_until_utc` with wall-clock for the per-timeframe map (`steps:L125-132`), added after a documented 2026-08 incident in which the top-level status stayed OK while every timeframe was stale (`steps:L136-150`).
